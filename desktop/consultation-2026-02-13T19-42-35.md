### Key observation from your samples
Your “old pipeline” fails because you’re asking the model to **re-solve the entire scene twice** (strip → restyle). Each pass re-interprets perspective, frame thickness, and window placement. Even with “lock composition” language, diffusion-style models don’t guarantee pixel-stable geometry across multiple edits.

The reference (Vorlage) works because it has:
- strong anchors (desk, shelves, plants)
- a very specific window frame proportion
- consistent perspective and horizon

So yes: **a single transform from V3 → themed should be more stable** than two transforms. But for togglable deco, **pixel-diff extraction is the wrong primary mechanism**.

## 1) Feasibility of “diff with/without deco” extraction
**Not reliable enough** for production-quality transparent overlays.

### Why it breaks
Even if the window stays “roughly” in place, you should expect between the two generations:
- micro-warping of edges (1–5 px locally, sometimes more)
- lighting/tonemapping changes on the desk surface
- texture noise differences (paper grain, wood grain)
- subtle parallax differences

A raw pixel diff will light up *everything* (especially on textured walls/wood), not just the removed objects.

### If you still want to try (best-possible diff algorithm)
Use a **robust alignment + perceptual diff** pipeline:

1. **Global alignment first**
   - Detect window rectangle (see section 5) in both images.
   - Compute a homography/affine transform to align “without deco” to “with deco” using the window corners + a few additional anchors (desk top corners, shelf corners).
   - Warp the “without” image to match the “with” image.

2. **Perceptual difference (not RGB diff)**
   - Convert to Lab.
   - Compute ΔE (CIEDE2000) per pixel.
   - Optionally add SSIM map to suppress low-frequency lighting shifts.

3. **Mask cleanup**
   - Threshold ΔE (you’ll tune per theme).
   - Morphological open/close to remove speckle.
   - Connected components: keep only blobs within expected deco zones (desk surface, shelves), reject large-area changes.
   - Feather edges (Gaussian blur) and generate alpha.

**Reality check:** even with all that, you’ll get halos, missing thin parts (plant stems), and false positives on textured backgrounds. It’s “okay for prototypes”, not great for a premium desktop product.

## 2) Better alternative for deco extraction (recommended)
### Best option: **Generate deco as transparent assets (images.generate) + fixed mount points**
This is the most controllable and least drift-prone.

**How it works**
- Your room scene (L1) is a single stable background per theme.
- Deco (L3) is a library of transparent PNGs (plants, cups, books, frames, etc.).
- In CSS you place them at predefined mount points (percent-based), with slight per-theme offsets if needed.

**Pros**
- True transparency.
- Toggleable by design.
- No dependence on pixel-identical backgrounds.
- You can reuse deco across themes (huge cost saver).

**Cons**
- Requires an initial “asset library build” effort.

### Second-best: **images.edit with masks for specific deco zones**
If you insist on “deco integrated into the painting style”:
- Keep one themed base.
- For each deco mount region, use **images.edit + mask** to inpaint “remove object” or “add object”.
But you said: *no transparent output from images.edit*, so this doesn’t directly produce overlays; it produces variants. It’s useful for generating **multiple baked arrangements**, not toggle layers.

### Practical recommendation
- **Do (b) as the main system** (transparent deco assets).
- Optionally use (c) to generate **2–3 baked “hero arrangements”** per theme for marketing screenshots, not for runtime toggles.

## 3) Minimizing window shift (composition stability)
### Yes: one-pass V3 → themed will be more stable
You remove one entire re-interpretation step, so drift drops a lot.

### Prompt techniques that actually help in images.edit
Use **explicit invariants + “only restyle” language** and forbid geometry edits:

**Core invariants to include every time**
- “Keep the exact camera position, perspective, and framing.”
- “Do not move, resize, rotate, or change the window opening.”
- “Keep window frame thickness and proportions identical.”
- “Preserve all straight lines; no warping.”
- “Only change materials, colors, lighting, and surface textures.”

**Anchors**
- Call out anchors: “desk edge stays perfectly horizontal”, “shelves remain at same height”, “window corners remain fixed”.

**Negative constraints**
- “No new windows, no extra frames, no thicker borders, no rounded corners unless already present.”

**Technical setting**
- Use `input_fidelity: "high"` for images.edit.
- Keep resolution consistent (1536×1024) to avoid resampling differences.

**Important:** Don’t ask for “remove objects” and “restyle” in the same pass if you care about geometry. Removing objects triggers bigger structural re-synthesis.

## 4) Optimal pipeline (min API calls, stable window, toggleable deco)
Here’s a production-friendly pipeline that hits your constraints.

### A) Establish a locked “geometry master”
1. Pick your best V3 (the Vorlage-like one).
2. Create a **Geometry Master** image:
   - Clean, neutral lighting, no UI overlay.
   - Window frame exactly as desired.
   - Desk + shelves included (structural anchors).
This is your single source of truth.

(You can do this once with images.edit if needed.)

### B) Generate L1 background per theme (5 themes × 2 modes)
**Goal:** 10 images total for L1.

For each theme:
1. **Light mode L1**: `images.edit` from Geometry Master → themed lighting/materials.
2. **Dark mode L1**: don’t regenerate from scratch; do `images.edit` using the Light L1 as input:
   - “Convert to night/dark mode lighting, keep geometry identical, preserve window position.”

This is **2 calls per theme = 10 calls**.

Why not CSS darkening? Because your scenes rely on believable light transport (lamps, moonlight, emissive panels). CSS filters look cheap fast.

### C) Generate reusable overlay libraries (one-time cost)
**L2 furniture overlays (optional):**
- If you truly need furniture toggles: generate as transparent PNGs via `images.generate`.
- But if furniture is structural and always present, bake it into L1 and skip L2 entirely.

**L3 deco overlays (recommended):**
- Build a **deco pack** per theme OR a shared pack with theme-tinted variants.
- Generate each deco item on transparent background:
  - “potted plant in ceramic pot, 3/4 view, soft painted style matching [theme], gentle shadow included, transparent background”
- Keep shadows subtle; place them via CSS.

**Cost control tip:** create **one neutral deco library** (plants, mugs, books) and then create **theme-specific colorways** using a small number of `images.edit` calls per asset batch (or accept neutral items across themes).

### D) Mount points + sprite sheet workflow
- Define mount points in percentages relative to the 1536×1024 canvas:
  - `desk_left_cluster`, `desk_right_cluster`, `shelf_left`, `shelf_right`, etc.
- Export each deco as PNG and optionally pack into sprite sheets (or keep separate files for caching).

This gives you deterministic toggles with zero geometry drift risk.

## 5) Per-theme CSS adjustment (window alignment)
You want the window rectangle to be consistent enough that CSS insets don’t change. But you also need a fallback.

### Best: fixed window mask/overlay system (recommended)
- Treat the “window opening” as a **known rectangle** in the master composition.
- In the app:
  - Render L1 scene.
  - Render the UI in a fixed CSS inset rectangle (same for all themes).
  - Optionally render a **window-frame overlay** layer on top (part of L2) to hide any minor mismatch.

This is the trick: even if the background window drifts 1–2%, the **frame overlay** (exactly aligned) will visually “force” the window to the correct spot.

**How to get the frame overlay**
- From the Geometry Master, create a window-frame-only PNG:
  - Either manually in Photoshop once (fast, perfect),
  - or generate via `images.generate` transparent “window frame overlay” matching the master (harder to match perfectly).
Manual wins here.

### Fallback: auto-detect window rectangle
Do (b) as a safety net:
- Run edge detection + Hough lines to find the largest rectangle with window-like border.
- Or simpler: template match against the master window frame.
- Store per-theme insets if detection confidence is high; otherwise use defaults.

**Do not** rely on manual measurement long-term; it doesn’t scale when you iterate.

## 6) Dark mode strategy
### Recommended: images.edit “relight” from the light version (not CSS filters)
- CSS filters destroy local contrast relationships and make materials look muddy.
- A single `images.edit` pass can introduce believable motivated lighting:
  - warm desk lamp, cooler moonlight, emissive space panels, etc.
- Keep geometry stable by using the already-themed light image as the input and `input_fidelity: high`.

If cost becomes critical later:
- Use CSS filters only for “preview” or low-end mode.
- Ship curated dark renders for premium.

# Final recommended architecture (summary)
**Do not diff-extract deco.** It will be fragile and time-consuming to clean.

**Instead:**
1. Create **one Geometry Master** with perfect window placement.
2. For each theme:
   - `images.edit` → L1 Light
   - `images.edit` → L1 Dark (from L1 Light)
3. Create **one fixed window-frame overlay PNG** (manual) used across all themes to guarantee CSS alignment.
4. Build **transparent deco library** with `images.generate(background="transparent")` + mount points.
5. Optional: auto-detect window rectangle only as QA/validation, not as the primary alignment mechanism.
