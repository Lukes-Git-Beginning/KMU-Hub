# Contributing — Cosmi / KMU Hub

Interner Beitrags-Leitfaden für die Cosmi-Codebase (Zentria UG i.G.). Die vollständigen
Architektur- und Entwicklungsrichtlinien stehen in [`CLAUDE.md`](CLAUDE.md); der Knowledge-Vault
unter [`.knowledge/`](.knowledge/) ist die Single Source of Truth für projektspezifisches Wissen.

## Branch-Strategie

- **Direct-to-main ist Default** (seit Sprint 1, 2026-04-18). Keine Feature-Branches, keine PRs —
  außer explizit gefordert (z. B. Security-kritische Änderungen, große Migrationen).
- **CI-Rot-Recovery:** `git revert <sha>`. **Nie** `reset --hard`, **nie** Force-Push auf `main`.
  ⚠ Ein deployter + revertierter Migrations-Commit strandet die Prod-DB auf höherer Version →
  forward-only fixen (Dateien zurück + neue Migration über dem Prod-Stand).

## Commit-Konventionen

- **Conventional Commits:** `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`
- Englisch, **imperativ** ("Add contact endpoint", nicht "Added…")
- **Keine AI-Attribution** — kein `Co-Authored-By`, kein "Generated by".
- Push am Ende jeder Session, um Divergenz zu vermeiden.

## Architektur-Regeln (verbindlich)

Vollständige Liste in [`CLAUDE.md`](CLAUDE.md) §Architektur-Regeln. Kernpunkte:

1. **Thick Services, Thin Handlers** — Business-Logik im Service-Layer, Handler nur Parse/Call/Respond.
2. **API-First** — OpenAPI-Spec (`backend/api/openapi.yaml`) vor Implementation.
3. **Migrations-Only** — Schema ausschließlich via golang-migrate (`make migrate-create name=xxx`),
   nie manuelles SQL. Jede neue Tabelle braucht `tenant_id UUID NOT NULL` + RLS-Policy (oder einen
   Eintrag in der System-Global-Liste, ADR-006).
4. **Structured Logging** — `slog`, kein `fmt.Println` / `console.log`.
5. **Config via Env-Vars** — `.env` nie committen. Neue `config.RequireX`-Assertions sind ein
   Prod-Deploy-Hazard: erst Compose-Passthrough + `.env.production`-Werte setzen, dann Assertion pushen.

## Build- & Test-Gates

**Backend** (`backend/`):

```bash
make build              # alle 24 cmd-Binaries
make test               # Unit-Tests + Race-Detector
make lint               # golangci-lint v2.8
make migrate-up
```

**Desktop** (`desktop/`):

```bash
npm run typecheck       # gescopt auf geänderte Dateien prüfen, nie Full-tsc als Gate
npm run lint            # unused-imports/no-unused-imports = ERROR
npm test                # Vitest
```

- **CI-Coverage-Gate:** 15 % gesamt (CI-enforced, Proto-Code gefiltert). Langfrist-Ziel 80 %+.
- **Gate-Checks nie durch Pipes** (`tsc | head` maskiert den Exit-Code) und nur auf dem **finalen Tree**.
- **CI hat zwei Push-Workflows:** `ci.yml` (Backend) und `ci-desktop.yml` — beide separat auf grün prüfen.

## Frontend-Modul-Standard (Build-+-Verify)

Für jede Frontend-Modul-Phase gilt dieselbe Schleife: bauen → i18n ×4 (`{var}`, nie `{{var}}`;
ICU-Plural) → Demo-/MSW-Handler → gescopter Typecheck → **Playwright-Screenshot-QA + die Screenshots
wirklich ansehen** → iterieren bis grün → ein Commit + Push. „Kompiliert" oder „Script lief grün"
allein reicht nicht. Exakter Prozess + Vorlagen: [`.planning/nico-block/WORKFLOW.md`](.planning/nico-block/WORKFLOW.md).

## Deployment

Production (Hetzner) deployt automatisch via `cd.yml` bei grünem CI auf `main`. Reihenfolge bei
manuellen Deploys: Backup → Assets bauen → Config → Code → Migrations → Restart → Health-Check →
Rollback-Plan bereithalten. Details in [`.knowledge/deployment.md`](.knowledge/deployment.md).
