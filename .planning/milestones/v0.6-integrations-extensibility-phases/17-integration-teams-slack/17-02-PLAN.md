    **forwarder.go** -- Platform-agnostic notification forwarder:
    ```go
    type Forwarder struct {
        repo       Repository
        teams      *teams.Client   // nil if Teams not configured
        slack      *slackadapter.Client   // nil if Slack not configured
        limiter    *RateLimiter
        cache      *MappingCache  // TTL cache of active channel mappings
    }
    ```
    - Constructor: `NewForwarder(repo Repository, teamsClient *teams.Client, slackClient *slackadapter.Client, limiter *RateLimiter) *Forwarder`
    - `HandleNotification(ctx, *models.Notification, *preference.DeliveryDecision)` -- this is the DeliveryCallback signature. It:
      1. Gets active mappings for the notification's ModuleID from cache (30s TTL per research)
      2. Applies most-specific-wins routing: if notification matches multiple mappings, only the most specific fires. Specificity: exact module match > wildcard. If two exact matches for same module (shouldn't happen), use the first.
      3. For each selected mapping, check rate limiter
      4. Dispatch to teams.Client or slack.Client in a goroutine (fire-and-forget, async per research anti-pattern)
      5. Log delivery result to integration_delivery_log via repo.LogDelivery
      6. On failure: increment consecutive failure counter. If >10 consecutive failures for a mapping, auto-disable the mapping (set is_active=false) and log error with slog
    - `MappingCache` is a simple struct with sync.RWMutex, map[string][]*ChannelMapping, lastRefresh time.Time, and 30s TTL
    - Bot-only identity by default per DSGVO recommendation (research discretion #1): notification cards show "KMU Hub" as sender, NOT actor name/avatar
    - Context-dependent action buttons based on event type:
      - HR leave events (hr.leave.requested): Acknowledge + Approve + Reject
      - Finance events (biz.invoice.*): Acknowledge only
      - Task/CRM events: Acknowledge + Reply
      - Default: Acknowledge only
    - Helper: `buildActionSet(eventTypeKey string) []ActionType` returns the list of action types for a notification's event type

    **rate_limiter.go** -- Per-channel token bucket:
    - `type RateLimiter struct` with sync.Mutex, map of channel_id -> bucket
    - Slack limit: 1 msg/sec/channel
    - Teams limit: 4 msg/sec (global across channels)
    - `Allow(platform, channelID string) bool` -- checks if a message can be sent now
    - `Wait(platform, channelID string) time.Duration` -- returns how long to wait
    - Simple implementation: last send time + minimum interval, no external dependencies

    **account_link_service.go** -- Account linking flow:
    - `type AccountLinkService struct` with repo Repository
    - `GenerateLinkToken(ctx, platform, externalUserID string) (token string, err error)`:
      1. Generate 32-byte random token
      2. SHA-256 hash it
      3. Invalidate any existing unused tokens for same platform+external_user_id
      4. Store LinkToken with 5-minute expiry
      5. Return raw token (not hash) for display to user
    - `VerifyAndLink(ctx, rawToken string, kmuhubUserID uuid.UUID) (*AccountLink, error)`:
      1. SHA-256 hash the raw token
      2. Look up by hash, check not used, check not expired
      3. Mark token as used
      4. Create/upsert account link
      5. Return the account link
    - `GetLinkStatus(ctx, platform string, kmuhubUserID uuid.UUID) (*AccountLink, error)`: check if user has a linked account
    - `Unlink(ctx, platform string, kmuhubUserID uuid.UUID) error`: delete account link

    **teams/client.go** -- Teams Bot Framework client:
    - `type Client struct` with msbotbuilder-go adapter, app_id, app_password
    - Constructor: `NewClient(appID, appPassword string) (*Client, error)` -- creates Bot Framework adapter
    - `PostNotification(ctx, mapping *ChannelMapping, notif *models.Notification) (*DeliveryResult, error)`:
      1. Build Adaptive Card via card_builder
      2. Get conversation reference from mapping.PlatformData
      3. Send proactive message via Bot Framework adapter
      4. Return DeliveryResult with platform_message_id (activity ID)
    - `UpdateCard(ctx, mapping *ChannelMapping, activityID string, updatedCard) error`:
      1. Update the existing activity with the new card (for in-place card updates after interactions)
    - `HandleIncomingActivity(ctx, req *http.Request) (*IncomingAction, error)`:
      1. Verify JWT token from Teams via adapter auth
      2. Parse Action.Execute invoke payload
      3. Extract action_type, notification_id, external_user_id
      4. Return structured IncomingAction for the webhook handler

    **teams/card_builder.go** -- Adaptive Card templates:
    - `func BuildCard(notif *models.Notification, actions []ActionType) adaptivecard.Card`:
      1. Create Adaptive Card v1.4 schema
      2. Accent container with module color from ModuleColors map
      3. Title text block (bold, medium size)
      4. Body text block (if notification.Body present)
      5. Module icon text (emoji-based: CRM=briefcase, HR=people, Finance=receipt, etc.)
      6. Context-dependent Action.Execute buttons from actions parameter:

        - Reply: "Antworten" button (opens task module input)
        - Approve: "Genehmigen" button (green accent)
        - Reject: "Ablehnen" button (red accent)
      7. Each action button carries data: {action_type, notification_id}
    - `func BuildUpdatedCard(notif *models.Notification, actionTaken string, actorName string) adaptivecard.Card`:
      1. Same card structure but with action result banner: "Gelesen von {actorName}" with checkmark, or "Genehmigt von {actorName}", etc.
      2. Action buttons removed (card is now resolved)

    **slack/client.go** -- Slack API client wrapper:
    - `type Client struct` with slack.Client (from slack-go/slack), bot token
    - Constructor: `NewClient(botToken string) *Client`
    - `PostNotification(ctx, mapping *ChannelMapping, notif *models.Notification) (*DeliveryResult, error)`:

    **slack/block_builder.go** -- Block Kit message templates:

      1. Header section with module icon emoji + bold title

      3. Context block with module name + timestamp

      5. Each button has action_id: "kmuhub_{action_type}" and value: notification_id
      6. Attachment color sidebar using module color from ModuleColors
    - `func BuildUpdatedBlocks(notif *models.Notification, actionTaken, actorName string) []slack.Block`:
      1. Same structure but with resolved banner section
      2. Actions block removed, replaced with context: "Gelesen von {actorName}"

    - `HandleCallback(w, r)` -- exchanges code for bot token, stores bot_access_token via vault key reference in integration_configs, redirects back to KMU Hub settings
    - Scopes needed: chat:write (post messages), commands (slash commands), incoming-webhook (unused but standard), users:read (resolve display names)

    **teams/webhook_handler.go** -- Teams inbound interaction handler:
    - `type WebhookHandler struct` with client *Client, repo Repository, linkService *AccountLinkService, notifService notification.Service-like interface
    - `HandleWebhook(w, r *http.Request)`:
      1. Client.HandleIncomingActivity verifies JWT and parses payload
      2. If activity is "invoke" with type "adaptiveCard/action":
        - Extract action data (action_type, notification_id) from Activity.Value
        - Resolve external user -> KMU Hub user via repo.GetAccountLink
        - If unlinked: respond with card saying "Bitte verknuepfen Sie Ihr Konto mit /kmuhub link"
        - Execute action based on action_type:
          - "acknowledge": call notifService.MarkRead with KMU Hub user ID
          - "reply": extract reply text from action data, create comment/response in appropriate module
          - "approve"/"reject": route to appropriate service (HR leave, etc.) -- for v1, emit a notification event that the automation engine or module-specific handler picks up
        - Respond within 5 seconds per Teams requirement: return updated card immediately, perform heavy work in goroutine
      3. If activity is "message" with text "/kmuhub link":
        - Generate link token via AccountLinkService
        - Respond with ephemeral message containing the token and instructions
      4. Bot Framework requires 200 OK response with optional card update

    **slack/webhook_handler.go** -- Slack inbound interaction handler:
    - `type WebhookHandler struct` with client *Client, signingSecret string, repo Repository, linkService *AccountLinkService, notifService (same interface)
    - `HandleInteraction(w, r *http.Request)`:
      1. Verify request signature using Slack signing secret (slack.VerifyRequest or manual HMAC-SHA256)
      2. Parse "payload" form field as slack.InteractionCallback
      3. For block_actions type:
        - Extract action_id (kmuhub_{type}) and value (notification_id)
        - Resolve external user via repo.GetAccountLink(PlatformSlack, callback.User.ID)
        - If unlinked: client.PostEphemeral with link instructions
        - Execute action (same pattern as Teams: acknowledge/reply/approve/reject)
        - Update original message in-place via client.UpdateMessage with BuildUpdatedBlocks
        - Respond 200 OK immediately (Slack expects fast response)
    - `HandleSlashCommand(w, r *http.Request)`:
      1. Verify signing secret
      2. Parse slash command payload
      3. If command is "/kmuhub" with text "link":
        - Generate link token via AccountLinkService
        - Respond with ephemeral JSON message containing token and instructions
      4. If command is "/kmuhub" with text "unlink":
        - Delete account link
        - Respond with confirmation
      5. Default: respond with help text listing available commands

    **notification_grpc.go** -- Extend existing NotificationGRPCServer:
    - Add integrationRepo and accountLinkService to server struct fields
    - Update constructor to accept these new dependencies
    - Implement 13 new RPCs from the proto extension:
      - ListIntegrationConfigs: list all configs, admin only
      - GetIntegrationConfig: get by platform, admin only
      - CreateIntegrationConfig: create config with vault key reference, admin only
      - UpdateIntegrationConfig: update is_active, metadata, admin only
      - DeleteIntegrationConfig: delete config + cascade mappings, admin only
      - TestIntegrationConfig: use forwarder to send a test notification to a specific channel, admin only
      - ListChannelMappings: list mappings for a config, admin only
      - CreateChannelMapping: create mapping with module list, admin only
      - UpdateChannelMapping: update channel, modules, is_active, admin only
      - DeleteChannelMapping: delete mapping, admin only
      - LinkAccount: verify link token and create account link (any authenticated user)
      - UnlinkAccount: remove account link (any authenticated user for own account)
      - GetAccountLinkStatus: check if current user has linked account (any authenticated user)

    **route_integration.go** -- Gateway HTTP routes:
    - `type IntegrationRoutes struct` implementing RouteRegistrar
    - ServiceName returns "notification" (reuses existing gRPC connection per Phase 14 pattern)
    - RegisterRoutes adds:
      **Admin config (auth + admin role required):**
      - GET /api/v1/integrations/configs -- list all configs
      - GET /api/v1/integrations/configs/{platform} -- get config by platform
      - POST /api/v1/integrations/configs -- create config
      - PUT /api/v1/integrations/configs/{platform} -- update config
      - DELETE /api/v1/integrations/configs/{platform} -- delete config
      - POST /api/v1/integrations/configs/{platform}/test -- send test notification

      **Channel mappings (auth + admin):**
      - GET /api/v1/integrations/configs/{platform}/mappings -- list mappings
      - POST /api/v1/integrations/configs/{platform}/mappings -- create mapping
      - PUT /api/v1/integrations/mappings/{id} -- update mapping
      - DELETE /api/v1/integrations/mappings/{id} -- delete mapping

      **Account linking (auth, any user):**
      - POST /api/v1/integrations/link -- verify token and link account
      - DELETE /api/v1/integrations/link/{platform} -- unlink account
      - GET /api/v1/integrations/link/{platform}/status -- check link status

      **Inbound webhooks (NO auth -- external platforms call these):**
      - POST /api/v1/integrations/teams/webhook -- Teams Bot Framework messaging endpoint
      - POST /api/v1/integrations/slack/interact -- Slack interactive message callback
      - POST /api/v1/integrations/slack/commands -- Slack slash command handler
      - GET /api/v1/integrations/slack/oauth/install -- Slack OAuth install redirect
      - GET /api/v1/integrations/slack/oauth/callback -- Slack OAuth callback

    - Inbound webhook routes bypass standard auth middleware but verify platform-specific signatures (Slack signing secret, Teams JWT)
    - Admin routes use existing RBAC middleware with admin role check
    - All handlers follow thin-handler pattern: parse request, call gRPC or direct service, format response
    - For inbound webhooks that need direct service access (not gRPC), inject the webhook handlers directly (same pattern as WOPI routes in Phase 11 which run at gateway level)
