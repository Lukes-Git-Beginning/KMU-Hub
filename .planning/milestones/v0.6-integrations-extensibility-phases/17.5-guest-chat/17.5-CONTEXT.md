# Phase 17.5: Guest Chat / Kundenportal - Context

**Gathered:** 2026-02-25
**Status:** Ready for planning

<domain>
## Phase Boundary

External website visitors can start a live chat with KMU Hub support agents via a shareable link (`/guest/:token`). Guest messages flow into the existing chat infrastructure and appear in the Unified Inbox as a new channel type. Agents respond from their normal Chat module or Unified Inbox. No Electron required for guests -- a separate lightweight web app served by the gateway.

This phase covers: guest session management, token-based authentication, WebSocket hub extension for guest connections, chat model extension (guest_session_id on messages), guest-specific rate limiting, a minimal guest web frontend, and Unified Inbox channel adapter integration.

This phase does NOT cover: embeddable JS widget for customer websites (future), admin configuration UI (Darien builds later), video calls for guests, email notifications to guests, or CAPTCHA integration (deferred to hardening pass).

</domain>

<decisions>
## Implementation Decisions

### Guest Authentication
- Token-based sessions via `guest_sessions` table (token_hash, channel_id, display_name, email, expires_at)
- Token generated server-side when admin creates a guest-enabled channel or via API
- Guest provides display_name (required) and email (optional) before entering chat
- Token expiry is configurable per channel (admin sets via API, default 7 days)
- No JWT for guests -- simple opaque token validated against DB, lighter weight
- Token passed as `?guest_token=xxx` query param for WebSocket, `X-Guest-Token` header for HTTP

### WebSocket Hub Extension
- Extend existing hub in `websocket.go` with `guestConnections` map (separate from `userConnections`)
- Guest auth path: `?guest_token=xxx` query param (parallel to JWT auth)
- Guests can only: send messages to their linked channel, receive messages from that channel, send/receive typing indicators
- Guests CANNOT: list channels, see presence, access search, view message history before their session, join other channels
- Typing indicators work automatically (channel-based broadcast, no change needed)

### Chat Model Extension
- Extend `chat_messages` with `guest_session_id UUID REFERENCES guest_sessions(id)`
- `created_by` becomes nullable with CHECK constraint: exactly one of (created_by, guest_session_id) must be set
- No separate `guest_messages` table -- single table, single timeline, threads work automatically
- New channel flag: `is_guest_enabled BOOLEAN DEFAULT false` on channels table
- Guest channels are normal channels that agents join -- no special channel type

### Guest Web Frontend
- Separate lightweight React SPA (NOT in Electron app)
- Served by gateway under `/guest/` as static files
- Reuses shared chat components where possible (or reimplements minimal versions)
- Route: `/guest/:token` -- token in URL, no login page
- Pre-chat form: display_name (required), email (optional), then enter chat
- Minimal UI: company branding (logo + primary color from config), message list, input box, file upload
- No sidebar, no header, no navigation -- just the chat window

### File Upload for Guests
- Allowed: images (PNG, JPG, GIF, WebP) + PDF
- Max size: 10MB per file
- Reuses existing MinIO infrastructure via gateway upload endpoint
- Stricter limits than employees (50MB, all file types)

### Unified Inbox Integration
- New channel adapter type `guest` in the Inbox system
- Guest messages appear in agent's Unified Inbox alongside email/chat/notification
- Deep link format: `/chat/{channelID}` (same as regular chat, agent navigates to guest channel)
- Agents can reply from Inbox or from Chat module -- both routes work

### Notification Flow
- When guest sends first message (new conversation): `notification.new` event to all channel members (agents)
- When guest sends subsequent messages: `notification.new` to assigned agent (or all if unassigned)
- Standard WebSocket push + notification bell -- no special sound or visual treatment
- Guest does NOT receive notifications (they see messages in real-time via WebSocket)

### Rate Limiting & Security
- 30 messages per minute per guest token (reuse integration framework rate limiter)
- IP-based throttling at gateway level (existing infrastructure)
- Auto-disable guest session after >10 failed token validations
- File upload: 10MB limit, image+PDF MIME type validation server-side
- Input sanitization: existing XSS protection applies to guest messages
- Token rotation: NOT in v1 (deferred)
- CAPTCHA: NOT in v1 (deferred to hardening pass)
- Abuse reporting: agent can deactivate a guest session via API

### Claude's Discretion
- Migration numbering (next available after existing migrations)
- Exact guest token format (UUID v4 recommended, SHA-256 hashed for storage)
- Guest web app build tooling (Vite standalone recommended)
- WebSocket message type naming for guest events (e.g., `guest.message.new`)
- Error response format for guest endpoints
- Exact rate limiter implementation (token bucket vs sliding window)
- Guest session cleanup strategy (cron vs lazy deletion on access)

</decisions>

<specifics>
## Specific Ideas

- Guest pre-chat form could include a "Betreff" (subject) field that becomes the first message or channel topic
- Guest sessions table should track `last_activity_at` for cleanup and analytics
- Consider `guest_config` table or JSONB column on channels for per-channel guest settings (welcome_message, logo_url, primary_color, token_expiry_hours)
- Guest messages should emit events via existing pg_notify for Automation Engine triggers (e.g., "new guest conversation" trigger)
- The guest web app should show a "Wir sind gerade nicht erreichbar" message when no agents are online (presence check)
- Agent assignment: first agent to reply claims the conversation (optimistic, like Unified Inbox claim pattern)
- Guest session should store `user_agent` and `ip_address` for abuse detection and analytics

</specifics>

<deferred>
## Deferred Ideas

- **Embed Widget (JS Snippet):** Phase 17.5 is link-only. Embeddable widget for customer websites is a future enhancement.
- **Admin Configuration UI:** Backend APIs are built in 17.5, but the Settings UI for configuring guest channels is deferred to Darien's frontend work.
- **CAPTCHA Integration:** Deferred to a security hardening pass. Rate limiting + IP throttling is sufficient for v1.
- **Token Rotation:** Guest tokens are static for the session duration. Rotation adds complexity without clear v1 benefit.
- **Video Calls for Guests:** Guests cannot initiate or join video calls. Text + files only.
- **Email Notifications to Guests:** When guest session expires, we do NOT email them. They must return via the link.
- **Guest Chat Analytics Dashboard:** Conversation metrics, response times, satisfaction scores -- future feature.
- **Chatbot / Auto-Responder:** Automated responses for common questions -- not in scope.
- **Multi-language Guest UI:** Guest frontend is German-only in v1 (DE-first strategy).

</deferred>
