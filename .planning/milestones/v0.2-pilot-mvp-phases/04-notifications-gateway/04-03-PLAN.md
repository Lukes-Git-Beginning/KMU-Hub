**route_notification.go** - Notification HTTP route handlers:

Create `NotificationRoutes` struct implementing the `RouteRegistrar` interface (from Plan 01). Follow the exact same pattern as route_auth.go, route_crm.go, etc.

```go
type NotificationRoutes struct {
    registry *ServiceRegistry
}
```

`getNotificationClient()` method: calls `registry.GetConnection("notification")`, returns `notificationv1.NewNotificationServiceClient(conn)`. If unavailable, handlers return 503.

Register these routes in `RegisterRoutes`:

```
POST /api/v1/notifications/read-all          -> HandleMarkAllRead
GET  /api/v1/notifications/unread-count      -> HandleGetUnreadCount
GET  /api/v1/notifications                   -> HandleListNotifications
POST /api/v1/notifications/{id}/read         -> HandleMarkRead

GET  /api/v1/notifications/preferences       -> HandleGetPreferences
PUT  /api/v1/notifications/preferences       -> HandleUpdatePreference
GET  /api/v1/notifications/event-types       -> HandleListEventTypes

POST /api/v1/notifications/mutes             -> HandleMuteResource
DELETE /api/v1/notifications/mutes            -> HandleUnmuteResource
GET  /api/v1/notifications/mutes             -> HandleListMutedResources

GET  /api/v1/notifications/quiet-hours       -> HandleGetQuietHours
PUT  /api/v1/notifications/quiet-hours       -> HandleUpdateQuietHours
POST /api/v1/notifications/dnd               -> HandleToggleDND
```

All routes require auth middleware. Apply `middleware.RequirePermission("notifications", "read")` for GET routes and `middleware.RequirePermission("notifications", "write")` for POST/PUT/DELETE routes.

Each handler:
1. Get notification gRPC client (return 503 if unavailable)
2. Extract user_id from auth context (middleware.GetUserID or equivalent -- check how existing handlers extract user ID)
3. Parse request body/params
4. Call gRPC method
5. Convert proto response to JSON
6. Respond

Handler specifics:
- `HandleListNotifications`: Parse query params `?limit=20&offset=0&module_id=chat&is_read=false`. Call ListNotifications RPC. Return paginated response with `{notifications: [...], total: N}`.
- `HandleGetUnreadCount`: Call GetUnreadCount RPC. Return `{unread_count: N}`.
- `HandleMarkRead`: Parse notification ID from URL. Call MarkNotificationRead RPC. Return 200 OK.
- `HandleMarkAllRead`: Call MarkAllNotificationsRead RPC. Return `{marked_count: N}`.
- `HandleGetPreferences`: Call GetNotificationPreferences RPC. Return preferences array.
- `HandleUpdatePreference`: Parse JSON body `{event_type_key?: string, module_id?: string, in_app: bool, desktop_push: bool, sound: string}`. Call UpdateNotificationPreference RPC.
- `HandleMuteResource`: Parse JSON body `{module_id: string, resource_id: string}`. Call MuteResource RPC.
- `HandleUnmuteResource`: Parse JSON body (or query params) `{module_id: string, resource_id: string}`. Call UnmuteResource RPC.
- `HandleListMutedResources`: Call ListMutedResources RPC. Return mutes array.
- `HandleGetQuietHours`: Call GetQuietHours RPC. Return quiet hours config.
- `HandleUpdateQuietHours`: Parse JSON body `{start_time: "18:00", end_time: "08:00", timezone: "Europe/Berlin", days_of_week: [1,2,3,4,5], enabled: true}`. Call UpdateQuietHours RPC.
- `HandleToggleDND`: Parse JSON body `{enabled: bool, until?: timestamp}`. Call ToggleManualDND RPC.
- `HandleListEventTypes`: Call ListEventTypes RPC. Return event types array.

**websocket.go** - Extend the WebSocket hub with notification support:

Add new message type constants:
```go
const (
    // Notification events (Server -> Client)
    WSNotificationNew         = "notification.new"
    WSNotificationRead        = "notification.read"
    WSNotificationReadAll     = "notification.read_all"
    WSNotificationUnreadCount = "notification.unread_count"
)
```

Add a public method `SendNotificationToUser`:
```go
func (h *WebSocketHub) SendNotificationToUser(ctx context.Context, userID string, notification interface{}, deliveryDecision interface{}) {
    msg := WSMessage{
        Type:    WSNotificationNew,
        Message: mustMarshal(map[string]interface{}{
            "notification":    notification,
            "desktop_push":    deliveryDecision has DesktopPush=true,
            "sound":           deliveryDecision sound field,
        }),
    }
    h.sendToUser(ctx, userID, msg)
}
```

Also add `SendNotificationRead` and `SendNotificationUnreadCount` methods that the gateway can call when mark-read operations happen (to sync across multiple connections of the same user).

The `SendNotificationToUser` method is what the delivery dispatcher callback (from Plan 02) will call. The gateway main.go wires this up.

**main.go** - Wire notification routes and delivery callback:

After Plan 01's refactoring, main.go uses ServiceRegistry. Add:
1. Register notification service: `registry.Register("notification", cfg.NotificationGRPCAddress)`
2. Create `NotificationRoutes` and add to the route registrars list
3. Wire the delivery callback: The notification service's event bus runs inside the notification microservice (cmd/notification/main.go). When it processes an event and decides to deliver, it needs to push to the WebSocket hub which lives in the gateway process. There are two approaches:

   **Approach A (Recommended)**: The notification gRPC service stores the notification in the database. The gateway polls or the notification service has a streaming RPC that the gateway subscribes to. This is complex.

   **Approach B (Practical for now)**: The gateway also runs a LISTEN on a `notification_delivery` channel. When the notification service decides to deliver a notification, it does `pg_notify('notification_delivery', ...)` with the user_id + notification data. The gateway's listener receives this and pushes to the WebSocket hub.

   **Approach C (Simplest)**: The notification service runs its event bus internally. After processing and storing a notification, it also emits a `pg_notify('notification_delivery', ...)` signal. The gateway has a lightweight listener on `notification_delivery` that just pushes to WebSocket.

   Use **Approach C**: Add a lightweight PostgreSQL LISTEN loop in the gateway (similar to the event bus but simpler -- just listens on `notification_delivery` channel and calls `wsHub.SendNotificationToUser`). This avoids streaming gRPC complexity while keeping the notification service and gateway decoupled.

   In main.go:
   - Create a dedicated pgx connection for LISTEN (not from the pool)
   - Start a goroutine that LISTENs on `notification_delivery` channel
   - On each notification: parse payload (user_id, notification JSON, delivery decision), call `wsHub.SendNotificationToUser`
   - Handle reconnection (same pattern as event bus but simpler)

   The notification service's ProcessEvent (in cmd/notification/main.go) needs to call `pg_notify('notification_delivery', ...)` after storing the notification. This means the notification service's notification repository Create method should also emit to `notification_delivery` channel. Update the postgres_repository Create method from Plan 02 accordingly (or add it as a hook in the service layer).

**Helper function**: Create a reusable helper for building and emitting event payloads to reduce boilerplate:
```go
// backend/internal/notification/event/emit.go
func EmitEvent(ctx context.Context, tx pgx.Tx, event models.EventPayload) error {
    payload, err := json.Marshal(event)
    if err != nil {
        return fmt.Errorf("marshal event: %w", err)
    }
    if len(payload) > 7500 { // safety margin below 8000 byte limit
        slog.Warn("event payload approaching NOTIFY limit", "size", len(payload), "type", event.Type)
    }
    _, err = tx.Exec(ctx, "SELECT pg_notify('events', $1)", string(payload))
    return err
}
```

Import this helper in CRM and Chat repositories. If the services don't use transactions for these operations, wrap the existing logic + pg_notify in a transaction.
