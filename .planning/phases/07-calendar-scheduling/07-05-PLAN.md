```go
type CalendarGRPCServer struct {
    calv1.UnimplementedCalendarServiceServer
    calendarService *calendar.Service
    eventService    *event.Service
    resourceService *resource.Service
    holidayService  *holiday.Service
    livekitService  *livekit.Service
}

func NewCalendarGRPCServer(

    holidaySvc *holiday.Service,
    livekitSvc *livekit.Service,
) *CalendarGRPCServer
```

Implement ALL CalendarService RPCs (~39 methods). Each method follows the thin handler pattern:
1. Parse proto request into service method params
2. Call the appropriate service method with uuid.Nil + isAdmin=true (gateway handles auth, same pattern as work_grpc.go)
3. Convert service response to proto response
4. Map errors via mapCalendarError function

Create converter functions:
- calendarToProto, calendarMemberToProto, eventToProto, expandedEventToProto
- attendeeToProto, exceptionToProto, reminderToProto
- resourceToProto, bookingToProto, holidayToProto
- categoryToProto, preferencesToProto, taskDeadlineToProto

Create mapCalendarError function mapping all sentinel errors to appropriate gRPC status codes:
- NotFound errors -> codes.NotFound
- Validation errors -> codes.InvalidArgument
- Permission errors -> codes.PermissionDenied
- Conflict errors (BookingConflictError) -> codes.AlreadyExists (include alternatives in status details)

type CalendarRoutes struct {

Register these HTTP endpoints (all under /api/v1/calendar/):

**Calendars:**
- GET /api/v1/calendar/calendars - list user's calendars
- POST /api/v1/calendar/calendars - create calendar
- GET /api/v1/calendar/calendars/{id} - get calendar
- PUT /api/v1/calendar/calendars/{id} - update calendar
- DELETE /api/v1/calendar/calendars/{id} - delete calendar
- GET /api/v1/calendar/calendars/{id}/members - list members
- POST /api/v1/calendar/calendars/{id}/members - add member
- DELETE /api/v1/calendar/calendars/{id}/members/{userId} - remove member
- PUT /api/v1/calendar/calendars/{id}/members/{userId}/permission - update permission
- GET /api/v1/calendar/browse - list browsable shared calendars
- POST /api/v1/calendar/calendars/{id}/subscribe - subscribe
- DELETE /api/v1/calendar/calendars/{id}/subscribe - unsubscribe

**Events:**
- GET /api/v1/calendar/events - list events in range (query: calendar_ids, start, end)
- POST /api/v1/calendar/events - create event
- GET /api/v1/calendar/events/{id} - get event
- PUT /api/v1/calendar/events/{id} - update event (non-recurring)
- PUT /api/v1/calendar/events/{id}/recurring - update recurring event (body: scope, original_date, changes)
- DELETE /api/v1/calendar/events/{id} - delete event
- GET /api/v1/calendar/events/{id}/attendees - list attendees
- POST /api/v1/calendar/events/{id}/rsvp - RSVP to event (body: status)
- PUT /api/v1/calendar/events/{id}/reminders - set reminders (body: minutes_before[])

**Categories:**
- GET /api/v1/calendar/categories - list user's categories
- POST /api/v1/calendar/categories - create category
- DELETE /api/v1/calendar/categories/{id} - delete category

**Resources:**
- GET /api/v1/calendar/resources - list resources (query: type, min_capacity, tags, floor)
- POST /api/v1/calendar/resources - create resource
- GET /api/v1/calendar/resources/{id} - get resource
- PUT /api/v1/calendar/resources/{id} - update resource
- DELETE /api/v1/calendar/resources/{id} - delete (soft)
- GET /api/v1/calendar/resources/{id}/availability - list bookings for date range
- POST /api/v1/calendar/bookings - book resource
- DELETE /api/v1/calendar/bookings/{id} - cancel booking

**Holidays:**
- GET /api/v1/calendar/holidays - list holidays (query: start, end, country, subdivision)
- POST /api/v1/calendar/holidays/seed - admin: seed holidays for year+country

**Preferences:**
- GET /api/v1/calendar/preferences - get user preferences
- PUT /api/v1/calendar/preferences - update preferences

**Task Deadlines:**
- GET /api/v1/calendar/task-deadlines - list task deadlines in range (query: start, end)

**LiveKit:**
- POST /api/v1/calendar/events/{id}/join-token - generate join token for video call event

Permission middleware: Use existing middleware.RequirePermission:
- calendars:read for GET endpoints
- calendars:write for POST/PUT/DELETE on calendars and events
- calendars:admin for calendar member management
- resources:read for GET resource endpoints
- resources:write for POST/PUT/DELETE on resources
- resources:read for booking endpoints (any authenticated user can book)

Each handler follows the thin pattern: parse request -> create proto request -> call gRPC -> parse proto response -> respond JSON.
