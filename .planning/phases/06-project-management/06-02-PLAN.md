**postgres_repository.go:**
Implement all repository methods using pgx/v5. Key patterns:
- Use `pgxpool.Pool` as constructor param (same as CRM repos)
- `List` query JOINs project_members to filter by user access (unless isAdmin)
- `List` includes subqueries for member_count and task_count
- `AddMember` uses ON CONFLICT DO NOTHING to handle idempotency
- `SaveAsTemplate` copies project row with is_template=true in a single INSERT...SELECT
- All queries use parameterized placeholders ($1, $2, etc.), NEVER string concatenation

**service.go:**
Service struct with `repo Repository` field. Constructor: `NewService(repo Repository) *Service`.

Key business logic:
- `Create`: Validate name (3-255 chars), validate project_key (2-10 uppercase alphanumeric), create project, auto-add creator as owner. Accept optional initial statuses; if none provided, do NOT add defaults (per locked decision: no global defaults imposed).
- `Get`: Check membership (or admin). Return project with details.
- `List`: Pass through to repo with user context.
- `Update`: Check ownership or admin. Validate fields.
- `Archive`: Check ownership or admin. Soft-delete via archived_at timestamp.
- `AddMember`: Only owner or admin can add. Validate role is valid.
- `RemoveMember`: Only owner or admin can remove. Cannot remove the last owner.
- `UpdateMemberRole`: Only owner or admin. Cannot demote the last owner from owner role.
- `SaveAsTemplate`: Only admin/manager can create templates. Copies project with is_template=true.
- `CreateFromTemplate`: Copies project, statuses, and returns new project. Task copying handled by task service (in 06-03).
- `GetUserPreference` / `SetUserPreference`: Validate view_type is "list" or "kanban".

Authorization pattern: Service receives userID and isAdmin from caller (gRPC server extracts from context). Service checks project membership via repo.IsMember() or repo.GetMember(). Admin bypasses membership check.

**postgres_repository.go:**
Implement all methods. Key details:
- `Reorder` updates sort_order in a loop within a transaction, setting sort_order = index for each statusID
- `CopyStatusesForProject` uses INSERT...SELECT to bulk copy statuses from source to target project with new UUIDs
- `Delete` should NOT cascade-delete tasks (status_id is SET NULL on delete per migration)

**service.go:**
Service with `repo Repository` field.

Key logic:
- `Create`: Validate name (1-100 chars), check duplicate name within project (case-insensitive), set sort_order to max+1
- `Update`: Validate name, check duplicate name (excluding self)
- `Delete`: Check no tasks use this status (or allow deletion -- status_id becomes NULL). Cannot delete if is_default=true.
- `Reorder`: Validate all provided IDs belong to the same project, then delegate to repo
- `CopyForProject`: Delegate to repo for template instantiation

No separate authorization here -- the project service handles membership checks. Status service trusts that the caller (gRPC server) has already verified project access.
