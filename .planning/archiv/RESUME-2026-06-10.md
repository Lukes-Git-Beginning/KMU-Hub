## 🗣 Entscheidungs-Protokoll (semi-autonom — ANGEPASST für Tag 2)
Es ist jemand da. Also bei einer Design-/Produkt-/Domänen-Unklarheit:
1. **Frag den anwesenden Treiber** (Nico bzw. Luke) — kurz, konkret, mit 2–3 Optionen. Treiber entscheidet → bauen → im Review-Faden notieren („Entscheidung mit <Treiber>: X").
2. **Nur wenn der Treiber unsicher ist ODER es Dariens Spezialwissen braucht** (z.B. Finanzberatungs-Domäne, strategische/visuelle Grundsatzfragen): sinnvollen Default bauen + im Review-Faden als „**offene Frage für Darien**" markieren, weiter (nicht blockieren).
3. Für „wie sieht gutes Cosmi-UI aus / wo gehört was hin": `DESIGN-DECISIONS.md` ist die Referenz — der Treiber kann damit auch selbst entscheiden.

→ Unterschied zum reinen Autonom-Modus: **erst fragen statt still defaulten**, weil ein Mensch da ist. Trotzdem nie lange blockieren.

## ⛔ KRITISCHE REGEL (Tag 2+): Branch FORTSETZEN, nicht neu erzeugen
Eure heutige Arbeit liegt auf eurem Strom-Branch. **NICHT** `git checkout -B marathon/<strom>` (das überschreibt den Branch von main und LÖSCHT die heutigen Commits).
Stattdessen zu Sessionbeginn **einmal**:
```bash
git fetch origin
git checkout main && git pull              # 1) aktuelle Handoff-Docs lesen (dieses Doc + HANDOFF-TEXTS liegen auf main)
git checkout marathon/<strom>              # 2) euren bestehenden Branch fortsetzen
git pull origin marathon/<strom>          #    eure gestrigen Commits holen
```
Danach `main` NICHT mehr mitten am Tag mergen/pullen. Weiter wie gehabt: pro Phase ein Commit → `git push origin marathon/<strom>`.
