# Nico-Runbook — Cosmi-Module bauen mit Claude Code

> Dein Handbuch, um Phasen aus dem Cosmi-Plan selbstständig abzuarbeiten. Block: **Content & Self-Service** (wiki · formulare · berichte · notifications).
> Prinzip: **Eine Phase = eine Spec-Datei.** Du arbeitest sie Schritt für Schritt ab, verifizierst selbst, meldest „fertig", Darien/Claude reviewt, dann die nächste.
> **Qualität vor Tempo.** Lieber eine Phase richtig als drei halb. Es gibt kein Zeitlimit.

---

## 0. Einmal-Setup (ca. 30–45 Min)

1. **Repo holen** (du arbeitest im selben Repo, Branch `main`, direct-to-main):
   ```
   git clone <KMU-Hub-Repo>
   cd "KMU Hub"
   git pull            # IMMER zuerst, vor jeder Session — Luke/Darien pushen oft
   ```
2. **Claude Code** installieren + im Repo-Root starten (`claude`).
3. **Dev-Umgebung** (im Ordner `desktop/`):
   ```
   npm install
   npm run dev         # startet Vite auf http://localhost:5173 — lass das Fenster offen
   ```
   Im Browser `http://localhost:5173` öffnen → die App läuft im Demo-Modus (ohne Backend).
4. **Playwright** (für die Screenshot-QA, einmalig, im Ordner `desktop/`):
   ```
   npm install -D playwright
   npx playwright install chromium
   ```
5. **Node-Check**: `node --version` (muss vorhanden sein, für i18n-Scripts + QA).
6. **Lies einmal** zur Orientierung: `CLAUDE.md` (Repo-Root) + diese Datei + **`WORKFLOW.md`** (der Verify-Prozess) + deine erste Phasen-Spec.

### Welche Claude-Code-Skills du nutzt
- **`frontend-design`** — wird automatisch geladen, sorgt für Cosmi-Design-Qualität. Nichts tun.
- **`/run`** — startet/zeigt die App, um eine Änderung im echten UI zu sehen.
- **`/verify`** — prüft, ob eine Änderung wirklich funktioniert (nicht nur kompiliert).
- **`/code-review`** (Stufe `medium`) — Selbstcheck deines Diffs vor „fertig".
- Bei UI-Politur optional: **`/polish`**, **`/critique`** (aus `impeccable`).
- **Nicht** selbst aufrufen musst du Skills nicht — sag Claude einfach in Worten was du willst, es wählt sie.

## 1. Die harten Regeln (nicht verhandelbar)

Diese Regeln gelten IMMER. Wenn Claude etwas vorschlägt, das dagegen verstößt → stop, korrigieren.

| Regel | Konkret |
|---|---|
| **i18n ×4** | Jeder sichtbare Text ist ein Übersetzungs-Key in `desktop/src/renderer/src/i18n/messages/{de,en,fr,it}.json`. **Nie** Text hart in Komponenten. Alle 4 Sprachen füllen. |
| **i18n-Klammern** | Interpolation mit **einfachen** Klammern: `{name}`, **nicht** `{{name}}`. Plural: `{count, plural, one {# Eintrag} other {# Einträge}}` (ICU-Syntax) — **nicht** `_one`/`_other`-Suffixe (die sind kaputt). |
| **Keine Emojis im UI** | Personality über Icons (lucide-react), Motion, Wording — nie Emojis. |
| **Keine ASCII-Umlaute** | In deutschen Texten echte Umlaute: „für" nicht „fuer", „löschen" nicht „loeschen". |
| **Keine sichtbaren Scrollbars** | Bestehende Scroll-Container-Muster wiederverwenden. |
| **Zurück-Button** | Jede Detail-/Unteransicht braucht einen Zurück-Weg. |
| **Wiederverwenden** | Komponenten aus `components/shared/` und `components/ui/` nutzen, nicht kopieren. Neue wiederverwendbare Teile in `shared/` bauen. |
| **Git** | Conventional Commits (`feat:`, `fix:`, `docs:`…), Englisch, imperativ. **Keine AI-Attribution** (kein „Co-Authored-By", kein „generated by"). Am Sessionende pushen. |
| **Animation** | Nur `transform`/`opacity` animieren (GPU). Tokens aus `lib/motion.ts`, keine Magic-Numbers. |

## 2. Der Phasen-Workflow (so läuft JEDE Phase ab)

1. **Pull**: `git pull` (Stand aktuell holen).
2. **Spec lesen + gegen Ist-Stand prüfen**: Öffne `.planning/nico-block/phase-XX-<name>.md`. Sie nennt Ziel, Dateien, Muster-Vorlage, i18n-Keys, Demo-Handler-Bedarf, Definition-of-Done (DoD). **Die Spec ist eine Momentaufnahme** — das Repo entwickelt sich schnell (Luke pusht in Wellen, teils 100+ Commits). Bevor du baust: kurz verifizieren, dass die Annahmen der Spec noch stimmen (existiert die UI schon? matchen die Hooks/Schemas?). **Bei Abweichung: melden, nicht blind bauen** (so wie bei Phase 01 geschehen — das ist genau richtig).
3. **Muster ansehen**: Die Spec verweist auf ein bereits gebautes Modul als Vorlage. Schau es dir an — du baust im gleichen Stil.
4. **Bauen** mit Claude Code: Gib Claude die Spec als Kontext („Wir arbeiten Phase XX ab, hier ist die Spec: …"). Arbeite die DoD-Punkte ab.
5. **i18n** in alle 4 Sprachen (Claude kann ein kleines Script schreiben wie die `add-*-i18n.mjs` in `desktop/scripts/`).
6. **Demo-Handler** falls die Spec sie verlangt (damit das Feature im Demo-Modus sichtbar funktioniert) — in `mocks/handlers/`.
7. **Selbst verifizieren** → Abschnitt 3.
8. **Commit + Push** (ein Commit pro Phase, klare Message).
9. **„Fertig" melden** an Darien/Claude mit: Phasen-Nr, Commit-SHA, Screenshots, ausgefüllte Verify-Checkliste.
10. **Review abwarten** → grün = nächste Phase; rot = Punkte nachbessern.

**Niemals zwei Phasen gleichzeitig** anfangen. Eine nach der anderen, jede grün abschließen.

## 3. Mandatory-Verify-Checkliste (vor „fertig" — ALLE Punkte)

Kopiere diese Liste in deine „fertig"-Meldung und hake jeden Punkt ab:

- [ ] **Typecheck grün**: gescopt über deine geänderten Dateien (Claude richtet ein `tsconfig.<phase>check.json` ein, das `tsconfig.web.json` erweitert und `global.d.ts` + `vite-env.d.ts` + `i18next.d.ts` + deine Dateien einschließt). `node_modules/.bin/tsc --noEmit -p tsconfig.<phase>check.json` → keine Fehler in DEINEN Dateien. ⚠ Nie einen Warte-Loop danebenlaufen lassen (bremst tsc aus).
- [ ] **QA-Script grün**: Claude schreibt ein `scripts/qa-<phase>.mjs` (Playwright gegen :5173), das die Kern-Funktion klickt + prüft. Läuft ohne `error`/`pageErrors`.
- [ ] **Keine Raw-Keys**: Im QA-Output + im Screenshot taucht KEIN `modul.irgendwas.key` als sichtbarer Text auf. (Häufigste Falle: doppelte Klammern oder fehlender Key.)
- [ ] **Alle 4 Sprachen** gefüllt (de/en/fr/it), keine fehlenden Keys.
- [ ] **Screenshots** bei voller Fensterbreite (1440px) — UI sieht sauber aus, keine abgeschnittenen Texte, keine Card-in-Card, keine Emojis.
- [ ] **Mehrere Zustände geprüft**: leer / mit Daten / Edge-Case (z.B. lange Texte). Keine leeren kaputten Screens.
- [ ] **Keine pageErrors** in der Browser-Konsole.
- [ ] **Demo funktioniert sichtbar**: Das Feature tut im Demo-Modus etwas Sichtbares (nicht nur „kompiliert").

Wenn ein Punkt nicht grün ist → **nicht** „fertig" melden, erst beheben.

---

## 4. Häufige Fallen (lies das, spart Stunden)

- **Doppelte i18n-Klammern** (`{{var}}`) → der Text wird roh angezeigt. Immer `{var}`. Nur per Screenshot-QA sichtbar, nicht im Typecheck!
- **Plural mit `_one`/`_other`** → kaputt im Demo. ICU-Syntax nutzen: `{count, plural, one {…} other {…}}`.
- **Feature ruft Endpoint, aber kein Demo-Handler** → leere/kaputte UI im Demo. Lösung: Demo-Handler in `mocks/handlers/` bauen (die Spec sagt, wann nötig).
- **Subagent baut ohne Verifikation** → Raw-Keys/Theme-Bruch schlüpfen durch. Immer selbst die Checkliste durchgehen, `tsc` allein reicht NICHT.
- **Theme-Bruch**: Farben nur über CSS-Variablen/Tailwind-Tokens (`text-foreground`, `bg-card`, `text-muted-foreground`…), nie Hex-Werte hart.
- **Full-Typecheck dauert ~20–30 Min** — deshalb immer gescopt prüfen (nur deine Dateien), nie das ganze Projekt als Gate.

---

## 5. Review-Gate (Übergabe an Darien/Claude)

Deine „fertig"-Meldung enthält:
1. **Phase**: Nr + Name
2. **Commit**: SHA + 1 Satz was drin ist
3. **Verify-Checkliste**: ausgefüllt (Abschnitt 3)
4. **Screenshots**: 1440px, Kern-Ansichten + Edge-Cases
5. **Offene Punkte**: alles wo du unsicher warst

→ Review prüft gegen die **Definition-of-Done** der Spec. Grün = nächste Phase. Rot = konkrete Nachbesser-Punkte, du iterierst.

**Bei Blockern** (etwas geht nicht, Backend fehlt, unklar): nicht raten — in `.planning/backend-gaps.md` notieren (für Luke) bzw. Darien/Claude fragen. Lieber kurz fragen als lange falsch bauen.
